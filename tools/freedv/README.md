# FreeDV reference tooling

`sources.json` records the first-milestone source pins and speech fixture hashes.
`reference_benchmark.py` runs the upstream FreeDV transmit and receive tools on
an exact pinned fixture. Both executables must already be built. Example, with
paths adjusted for the local source/build locations:

```sh
python3 tools/freedv/reference_benchmark.py --mode 700E \
  --tx /path/to/codec2-build/src/freedv_tx --rx /path/to/codec2-build/src/freedv_rx \
  --input /path/to/codec2/raw/ve9qrp_10s.raw --output /path/to/new-results

python3 tools/freedv/reference_benchmark.py --mode RADE-V1 \
  --tx /path/to/rade-build/src/rade_tx_wav --rx /path/to/rade-build/src/rade_rx_wav \
  --input /path/to/rade_c/input_sample.wav --output /path/to/new-results
```

The output directory must not exist. Each run writes logs and `result.json`;
its temporary audio files are deleted. Fixture hashes are checked before running.
The real-time factor is whole-file wall time divided by input duration, including
process and file I/O. It is an **unpaced reference measurement**, not the planned
30-minute streaming benchmark, p99 block-time test or an on-radio qualification.
It does not access or control the radio. The complete milestone scope and its
outstanding requirements are in `docs/freedv/milestone-1.md`.

`validate_rade_v1_loss.sh` runs the upstream `rade_c_v1_wav` feature-loss
check with the pinned RADE and RADAE sources and the expected input hash. It
requires a built RADE tree and a Python environment with PyTorch, NumPy and
Matplotlib. Pass RADAE source, RADE source, RADE build, Python interpreter and a
new output directory, in that order. It preserves each tool's exit status and
requires the upstream `PASS` marker. This is a host reference check, not RF or
radio performance validation.

`codec2_frame_bench.c` is a separate 700E codec-only prototype. Build it against
the pinned Codec2 headers and library, for example:

```sh
cc -std=c11 -Wall -Wextra -Werror -I/path/to/codec2/src \
  tools/freedv/codec2_frame_bench.c -L/path/to/codec2-build/src -lcodec2 -lsamplerate -lm -o /tmp/codec2-frame-bench
/tmp/codec2-frame-bench tx /path/to/codec2/raw/ve9qrp_10s.raw 10 paced resample 1
```

For RX, pass a raw 8 kHz signed-16 modem fixture generated by the pinned
`freedv_tx 700E` tool and use `rx` instead of `tx`. Fixtures repeat from memory;
the program has no radio or physical audio I/O. It reports frame timing ratios,
deadline misses and Linux peak RSS as JSON. The optional `resample 1` arguments
exercise stateful 44.1-to-8 kHz and 8-to-44.1 kHz libsamplerate conversion,
including the output conversion to signed 16-bit PCM, and
exclude one second of audio from timing. The 8 kHz fixture is converted to
44.1 kHz before measurement, then repeated from memory. Omit both arguments for
the original codec-only timing. Unpaced runs report deadline misses as null.
Full-pipeline qualification remains false: RADE, live audio-device scheduling,
queue/underrun accounting and on-radio validation are not implemented.
Do not use its numbers to claim the milestone performance gate passed.
The prototype has been exercised both natively and under ARM/QEMU. QEMU timing
is not representative of the radio, and the Debian ARM build is not a deployable
substitute for the matching X6200 Buildroot SDK.

`diagnostic_state.c` is an isolated session-state prototype. It does not control
the radio, provide synchronization, capture snapshots, or implement the diagnostic
UI. Its caller must serialize access, stop audio and clear software TX when
requested, and complete restoration before calling `fd_restored`. Compile and run
the behavioral check with:

```sh
cc -std=c11 -Wall -Wextra -Werror tools/freedv/diagnostic_state.c \
  tools/freedv/diagnostic_state_test.c -o /tmp/freedv-state-test
/tmp/freedv-state-test
```

For the host GUI build, configure with `-DENABLE_FREEDV_DIAGNOSTICS=ON` and run
`ctest --test-dir build-host -R '^freedv_diagnostic_state$' --output-on-failure`.
The option defaults to OFF. When enabled on X6200 or the host simulator,
Settings → Info includes a read-only snapshot of cached route commands, the
last radio state and the most recent baseband packet's TX flag and age. It does
not acquire a session, run experiments, or key RF; the values are refreshed when
the Info page opens. Cached commands are not hardware readback, and unknown or
old packet status must not be taken as proof that RF has stopped.

With a freshly started host simulator and `tesseract` installed, run
`python3 tools/freedv/host_ui_check.py` to exercise opening Settings. Add
`--snapshot` for a diagnostics-enabled build to check the displayed route
snapshot. The helper drives host FIFOs and reads only the local simulator screen;
do not use it on a physical radio.

To also test decoding the X6200 control library's cached RECORD, MODEM and PTT
bits, provide `-DX6200_CONTROL_INCLUDE_DIR=/path/to/X6200Control/include` when
configuring the host build and build target `freedv_x6200_route_test`. Run
`ctest --test-dir build-host -R '^freedv_' --output-on-failure`. This mocked
test covers all eight bit combinations; it does not read actual hardware.
`radio_get_commanded_audio_route()` reads those commands under the radio lock;
it returns the last known state and timestamped packet TX flag separately and
is not a complete route snapshot. Before the first packet, or if the supplied
clock predates the packet, the packet status is unknown. A caller must decide
which packet age is usable; this accessor does not decide whether RF is safe.

`inventory.py --output /path/to/new-inventory.json` collects kernel, CPU and
memory information and lists available ALSA/PulseAudio devices. It does not
collect station settings or change the radio. Missing commands are recorded as
unavailable. The output may include local audio-device names; inspect it before
sharing. The inventory is not a hardware routing or TX test.
